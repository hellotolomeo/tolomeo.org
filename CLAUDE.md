# tolomeo.org

Portfolio site for Tolomeo. Static, pre-rendered, hosted on GitHub Pages at tolomeo.org.
The spec is `BRIEF.md` (v2); decisions on the build plan are in `BUILD-PLAN-RESPONSE.md`. Read both before any change to layout, behaviour or content model. The **look** in `BRIEF.md` §3 and §5 and in `design/*.html` (dark, pink lines) is superseded by the redesign of 11 Nov 2026: its values are the "Design" section below.

## Stack
- The Zeldman Pattern, vendored in upstream's own `AGENTS.md` layout (`client/lib/`, `lib/vendor/`, `lib/filters.js`, `server/zeldman/`, docs in `lib/zeldman/`). One component = `components/<name>.html` + `.css` + `.js`. `setState()` is the only way the DOM changes. No inline `style=""` in component markup; generated proportions go in `dist/client/covers.css` and `dist/client/slides.css`.
- Node renders everything at build time: `node build.js` → `dist/`. No server in production.
- Content is Markdown + YAML front matter in `content/` (projects, site). Images in `images/projects/<slug>/`; the CMS stores full `/images/…` paths and drops empty keys, so the data layer defaults every field.
- Pages CMS edits content via `.pages.yml`. Keep the field names in `.pages.yml`, `content/` and the templates identical.
- GitHub Actions builds and deploys `dist/` on every push to `main`.

## Commands
- `npm run dev` — local server on http://localhost:3100 with live template reload
- `npm run build` — write `dist/` (resizes images with sharp, cached by hash)
- `npm run images -- <folder-of-originals> <slug>` — optional bulk tool: 2000px web copies in `images/projects/<slug>/`
- `npm run verify` — after a build: Playwright checks for the acceptance points (CI runs it on branches and PRs, not on `main`). Needs Chromium: `npx playwright install chromium`, or `CHROMIUM_PATH`.
- `node scripts/normalize-images.js` — what CI runs before the build: HEIC/TIFF → JPEG, >2000px shrunk, content references rewritten; idempotent.
- `node scripts/import-site-data.js <kit-folder> [--dry-run]` — the one-off import of a Claude Design site kit (a folder with `site-data.json`, `thumbnails/`, `images/`): rewrites `content/projects/`, copies the photos and thumbnails into `images/projects/<slug>/`, deletes photos nothing references. Already run for the redesign of 11 Nov 2026; content in `content/` (edited in the CMS) is now the source of truth.
- `scripts/import-projects.py` (the spreadsheet importer) and `scripts/import-covers.js` (the design-canvas cover migration) are **superseded: don't run them** — the first would bring back the spreadsheet's typos, old titles and publish states, the second writes `cover_style`/`cover_focus`/`cover_zoom`, which no longer exist.

## Rules
- Never edit `dist/`; it is generated.
- Never invent content: empty descriptions and missing images stay empty. Placeholders only where the design needs an image.
- Design values come from the "Design" section below (the redesign of 11 Nov 2026, which replaced `design/*.html` and the token table in `BRIEF.md` §3). Don't restyle.
- Plain JS, plain CSS, no bundler, no framework, no TypeScript. Dependencies stay: `nunjucks`, `gray-matter`, `marked`, `sharp`; `playwright` (pinned to the installed browser's version) is the only dev dependency, for `scripts/verify.js`.
- Every page must be complete HTML before JavaScript; the first browser render must make zero DOM mutations.
- Every `BRIEF.md` §9 assumption that still applies is a constant in `site.config.js` (the redesign removed the hover photo and the frame jitter, and their constants with them).
- Anything Tolomeo edits must be editable alone in Pages CMS. Scripts are for one-off migrations only.

## Design (redesign of 11 Nov 2026)
One light colour world, no visible lines anywhere. Reference width 1366px (project pages: 1366 × 710).

| Token (`client/site.css`) | Value |
| --- | --- |
| Ground / text | `#f2f2f2` / `#412d37` |
| `--link`: link hover, the Index header line, chevrons, focus ring | `#99567a` |
| `--tag`: the Index list's type labels (67% of the text colour; `TAG_COLOR`) | `#807279` |
| `--caption` (80%) | `#67575f` |
| `--thumb`: scroll bars (solid), the page's own included (`scrollbar-color` on `html`) | `#ccabbd`, 8px, rounded |
| Frame, on every thumbnail and every project photo | 6px `#f4f3e7`, `box-shadow: 1px 2px 6px rgba(100, 40, 95, 0.55)` |

- Type: Fluxisch Else only. Body Light 12px / 16px (the design gave 13.38px; the owner asked for 12px on 18 Nov 2026, and the 16px line was kept so that nothing else moves). Bold (the second `@font-face`, `fonts/FluxischElse-Bold.woff2`) for the Index's dates, titles, `Back`, the words `type` / `role` / `for` on a project page and `**bold**` in content. No italic exists: slanted text is Light with `transform: skewX(-6deg)` on an inline-block; Markdown `*italic*` becomes `<em>` with one `<span>` per word (`server/markdown.js`) so it still wraps; punctuation that touches the slanted text is tied to its word in an unskewed `<span class="nb">`, so a line never starts with the comma after a *Title*. Word spans inside a link take the link's underline (`a em, a span { text-decoration: inherit }`), which an inline-block otherwise drops. Links are underlined 0.67px in the text colour and turn `--link` on hover.
- Tab title: the home page is `Tolomeo`; every other page `Tolomeo — <page>`. Favicons are the files in `public/`, which is copied to the site root.
- **Index**: an 88px header (`.site-head`, outside the component): one purple line at 37px / 33px, from `site/index.md` `intro` (Markdown; its link is the name, Bold, text colour, to `/info/`). Side by side (from 720px) the line keeps to the grid's half: it wraps 16px before the middle of the page (`max-width: calc(50% - 26.5px)` of the header's content box, which is the page less its 37px and 16px paddings, so that is half the page, less 16px, less the 37px inset), and the 88px header has room for its two lines. No "Index" link. Under it, from 720px wide, two 50% columns. Left: the grid, 2 columns, a cell a quarter of the page wide at 341.2 : 197.12; each thumbnail whole, centred, as large as fits 91% × 86.5% of the cell, frame included. Right: the list; a row is one fifth of a cell tall (`2.8886cqw`), the date at 1.676% of the page from the column's edge, the title at 9.868%, the type 15px after the title, sub-items with a `•`. Pointing at a row or its thumbnail turns the title `--link` and shows a 12.4 × 14.3 chevron (1.5px stroke) 14px left of the title. Thumbnails are static.
- **Index below 720px** (phones): the grid is one column and the whole list (dates, titles, types, filter) comes under it. A cell is the page wide and only as tall as what is in it: the thumbnail by the same rule (whole, framed, centred, as large as fits 91% of the cell's width and 49.9733% of that width in height, frame included, which is about twice its size two to a row), then the project's title and nothing else (no date, no type). The title is set like the list's titles (Bold 12px / 16px, text colour, no underline), centred, a long one wrapping in balanced lines within 91% of the page; it sits 10px under its own frame and 32px before the next frame, and turns `--link` when the thumbnail is pointed at or has focus. The first frame is 16px under the header; the list's first row starts 48px under the last title. A project without a thumbnail shows just its title.
- **Project page**: a 79px header (`Back` at 37px / 42px to `/`; the title centred, Bold, text top 43px, a link to `#project-info`) that stays at the top of the window while the page scrolls under it: the ground colour behind it, no line, no shadow. Then the photos in **sets** (`images[].set`: a whole number, 1 when left out), one set under the other in ascending number order, each one window tall under the header, with no title or label of its own; after the last set, `#project-info`. A set shows its photos one at a time, framed, centred, as large as fits between the header and the caption's room (568px tall at a 710px viewport), never cropped; chevrons 16.5 × 19 (1.5px stroke) 28px either side of the frame in 44 × 44 targets, none before the set's first photo or after its last; a click on the photo and the left / right keys also move (the keys: the set on screen, and only that one). Caption 16px under the frame, at most 480px wide, 11px / 13.2px, `--caption`. With a mouse or trackpad the page snaps: set by set, then to the information; touch screens scroll freely. A project with one set is the page as it always was: the photos, then the information. `#project-info` (the layout of 18 Nov 2026) is a screen of its own, and the project's title is **not** repeated in it: the header is the only place it appears. From 760px wide it is two columns either side of the page's centreline, in fixed px (the type does not scale). Left, from 318px left of the centreline: one line each for `type:` (the tags, comma-separated), `role:` and `for:` (the client), then one empty line, then the years; on an 18.73px line (the step in the owner's image, which was drawn at 13.38px type on a 1.4 line; kept in px when the type went to 12px, so the lines stay where the image has them), `type:`, `role:` and `for:` Bold, colon included (the owner's image has it so: a Bold colon is 2px narrower on the page than a Light one, and the values start where the image's do), everything else Light. Right, from 8px right of the centreline: the description, at most 312px wide, 16px lines, 7px between paragraphs, the photo links under it if there are any. All of it is the text colour and upright (no `--tag`, no slant; a `*title*` inside the description still slants). At rest the description's first line box is 74px from the top of the window, and the two columns' first lines share a baseline. A line whose value is empty is left out, label and all; with none of the three there is no empty line above the years. Two arrows link to the project before and the project after in the Index's order, none before the first project or after the last: the photos' 16.5 × 19 chevron in `--link`, each in a 44 × 44 target, the left one's edge 329px left of the centreline and the right one's 337px right of it, their middle at 74.5% of the window's height when the section is at rest; they scroll with the section. Below 760px it is one column under `Back`: the lines, 24px, the description (at most 433px), 24px, then the two arrows in a row, previous at the left of the page and next at the right; in one column the section rests 16px lower, its top at 88px, clear of a header whose title takes two lines.
- **Info**: `Back` at 37px / 42px; the text from 113px down, at most 420px wide, 7px between paragraphs.

## Conventions
- Data flows one way: `server/content.js` shapes everything (sorting, defaults, image lookups, Markdown → HTML via `server/markdown.js`); templates only print flat fields. `build.js` and `server.js` share it and `server/routes.js`.
- Components: `project-index` (home: grid + list + filter; props `projects, filter, match`, state `hover`) and `project-slides` (one set of a project page's photos, so a page has one per set; props `images, label, eager`, state `index, near`). Page-level styles are `client/site.css` (every page, with the Index header and the Info / 404 frame) and `client/project.css` (the project page's header and information).
- Browser-only template variables (`shown`, `hover`, `index`, `near`) are guarded with `| default(…)` so the server render and the first browser render are identical. Keep it that way; `npm run verify` measures it.
- Templates are preloaded with `fetch()` by `client/template-env.js` `setup([...])`; list every template (and partial) a page's components use in that page's entry (`client/main.js`, `client/project.js`).
- Measures the design gives as a share of the 1366px page are `cqw` on a page-wide container (`project-index`; `main.project`), so they scale with the page and ignore the scrollbar; at ≥720px the grid's two columns are `25cqw` each for the same reason (where the native scrollbar shows, it lies over the right cells' margin instead of shrinking them). Type stays 12px, so two things give way on narrower side-by-side pages, and only there: below about 1270px the date column's 104px floor (the smallest that keeps the hover chevron clear of the longest date) puts the title right of 9.868%; below 1108px a row's `line-height` is the row height, so a row whose type wraps takes exactly two (or three) row slots and five slots are still one cell. From 1108px up a wrapped row's two 16px lines fit inside one slot.
- No comments in CSS (`lib/zeldman/AGENTS.md`); the derivations live here. Grid thumbnail: `49.9733cqw` is 86.5% of the cell's height as a share of its width (197.12 / 341.2 × 86.5), and both limits lose 12px for the frame. That `cqw` is the cell's own width (every `.cell` is a container), so below 720px, where a cell is the page wide and has no fixed proportion (`aspect-ratio: auto`), the same line limits a thumbnail to 91% of the page's width and 49.9733% of it in height. `coverSizes()` in `server/content.js` says the same in `sizes` (a cell is a quarter of the page from 720px, the whole page below), so a phone takes a file sharp enough for its larger thumbnail. Slideshow (`components/project-slides.css`): `--head` 79px is the page header; `--cap` 63px is the caption's room (16px gap, three 13.2px lines, 7.4px), kept on every slide so a photo that fills the height sits directly under the header; `--h` is what is left of the viewport (`svh`); `--w` is the page less, on each side, a 44px chevron target, a 14.25px gap (the 16.5px chevron is centred in its target, so that puts it 28px from the frame) and a 16px edge; at ≤600px the gap and edge are 0. A photo limited by width instead of height is centred in the slide. The caption's limit is 512px because its 16px side padding is inside it: 480px of text.
- Framed boxes are never cropped: each takes its image's proportions from a generated rule, never inline: `--a` per grid cell in `client/covers.css` (`coversCss()`), per project photo in `client/slides.css` (`slidesCss()`, loaded by project pages only: `#slides-<slug>-<n> .slide:nth-child(<i>)`, `<n>` the set's place on the page, 1 for the first, whatever its number), both in `server/content.js`. One thumbnail style for all: `cover_style`, `cover_focus`, `cover_zoom` and `hover_image` are gone from the content, the CMS and the data layer, and so is the thumbnail tuner.
- Index layout at ≥720px: the page does not scroll; each column is its own scroller (`.images .scroll`, `.rows`) under the header; native scrollbars are hidden and the thumbs are a CSS scroll-driven animation (`.track`/`.thumb`, no script; where `animation-timeline` isn't supported the native scrollbar shows, thin, in the thumb colour): the grid's at the right edge of its column, the list's at the right edge of the page. Below 720px: normal page flow, the grid one column (`.grid` and `.cell` are each one `minmax(0, 1fr)` track), the list under it.
- The title under a thumbnail is `<span class="name">` inside the cell's link, in the server's HTML for every cell at every width and `display: none` outside the `max-width: 719.98px` block: the stylesheet shows it, never script, so the first render still makes no mutation and nothing changes from 720px up. The link's name for assistive technology stays its `aria-label`. `.name` shares the list titles' weight rule (`.years, .title, .name`), so the two can't drift apart. The phone measures: a cell has 16px of padding above and below and `.name` a 10px top margin after a `.box`, which makes 10px under the frame and 16 + 16 = 32px to the next one; `max-width: 91cqw` and `text-wrap: balance` wrap a long title; `.index` has 32px above it there (16px while the grid was two columns), so the list starts 48px under the last title, further than the next thumbnail would be. The title turns `--link` by CSS (`.cell:is(:hover, :focus) .name`); the `hover` state still touches only the row.
- Row highlight: the `hover` state puts class `on` on the row (pointer on the row or its thumbnail, or focus); the chevron is a CSS mask on `.what::before`, drawn at 12.4 × 14.3 inside a whole-pixel box (a mask stretched to a fractional box is snapped to whole pixels). The scroll thumbs have two animations on the column's scroll timeline: one moves the thumb, the other only makes it visible and runs over twice the range so it never finishes (a finished animation keeps its last value when a filter leaves the column with nothing to scroll, which left a thumb behind). Tags are `<button>`s that toggle the filter (`?filter=a,b`, any-match); active ones are in the text colour.
- Sets: `server/content.js` groups a project's photos by `images[].set` (`normalize()` defaults it to 1; anything that is not a whole number from 1 is 1, with a warning) into `project.sets`, ascending by number (the numbers need not be consecutive, nor the list grouped), the photos of a set in list order; a set none of whose photos exist is left out. `shared/pages/project.html` prints one `<project-slides>` per set, then `#project-info`. A set's `label` is `Photos of <title>`, or `Photos of <title>, set 2 of 3` when there are several. `project.scripted` (some set has more than one photo) decides whether the page loads its scripts at all.
- The slideshow (each set is one): every photo is in the HTML; `index` puts class `current` on one slide and the stylesheet hides the rest **only when the element is `:defined`**, so with JavaScript off (or not yet loaded) the photos of every set are one under the other, in set order, the first exactly where the script shows it. Each slide prints its own chevrons (none on the first's left or the last's right, so none at all in a set of one photo), so they sit beside the frame by layout; when the photo changes while a chevron has focus, focus moves to the same chevron of the new slide (the other one at either end). Each set keeps its own `index`. Every set hears the left / right keys and only the one on screen moves: the one whose box covers the middle of the window below the header (`onScreen()`, which reads `--head`); while the information is there, none does.
- Loading: the first set's tag carries `eager`, and there the current photo and the next are `loading="eager"`, the rest `lazy` (`loading` follows `index`). In every other set all photos start `lazy`, so the browser fetches a set's first photo as the set comes near and nothing else; `near` (set once, when a scroll brings any of the set into the window, or when the set is moved) then makes its current photo and the next eager as well. `near` changes only on a scroll or a move, never on connect, so the first render is the server's HTML for every set.
- The project page's scroll (`client/project.css`, which only project pages load): `.project-head` is `position: sticky; top: 0` with a `z-index` above the photos, so a title that wraps still pushes the content down by its real height; `html` has `scroll-padding-top: 79px`, the header's height, so every set lands under it; `.project-info` has `scroll-margin-top: -7px` on top of that, so the title link (`#project-info`) and the snap both rest it with its top at 72px. That is 7px above the header's lower edge and 1px below the header's ground colour (which stops at 71px, see the 8px measures), so none of its text is covered. Below 760px, in one column, where nothing depends on the 74px, `scroll-margin-top` is `9px` instead and the section rests with its top at 88px: where a title wraps (at 320px wide for the two longest) the header is one 16px line taller than 79px and its ground colour reaches 87px, which at 72px covered the whole first line; 9px is those 16px less the 7px, and the first line then starts at 89px. (Plain CSS does not know the header's real height: a title of three lines would still cover that line, and a set of photos still lands 16px under a header of two.) Under `@media (hover: hover) and (pointer: fine)` `html` is `scroll-snap-type: y mandatory`; each set is a snap target at its start with `scroll-snap-stop: always`, and so is `.project-info`, whose `min-height` is the window less those 72px (less 88px below 760px): it gets a screen of its own, the page can always scroll far enough for it to rest there, and it starts exactly at the window's lower edge while the last set is at rest, so nothing of it shows under the photos. A section taller than the window (a long description in a small window) is a snap area larger than the window: the browser lets it scroll freely inside, so all of it can be reached. Snapping waits for the sets: while a set of several photos is not yet `:defined` (the script still loading, or JavaScript off) its photos are one under the other, and `html:has(project-slides:not(:defined) .slide + .slide)` turns snapping off, so that state scrolls freely. Don't remove that rule: with snapping on in that state, Chromium started a smooth scroll to the end of the page by itself in about 1 load in 100 (measured over thousands of loads; none with the rule). A page whose sets hold one photo each has no such state and snaps without a script. In Chromium a wheel snaps to the nearest stop when it ends: a turn of less than half a window goes back, and a single very long one can still pass a set (`scroll-snap-stop` holds for the keyboard and for touch). A project with no photos has the section as the first child of `main`, in the flow under the header at 79px, where that `min-height` would make the page 7px taller than the window (a page that snaps 7px down on load, or scrolls 7px for nothing): from 760px `.project > .project-info:first-child` has `margin-top: -7px`, so it lies where it rests, at 72px, in a page exactly one window tall; below 760px it has `min-height: 0` and is as tall as its text, under the header whatever the header's height. A page opened at `#project-info` (a link from elsewhere, an address): the browser sets off for the section, smoothly where `site.css` asks for it, while the sets are not yet defined and the page is many photos taller; once they are defined the page is shorter and that scroll simply ends at the end of the page, which left the first lines of a section taller than the window under the header. So `client/project.js`, after the component is defined, calls `scrollIntoView()` on the section once, when `location.hash` is `#project-info` and the navigation's type is `navigate` (a reload or the back button brings back the reader's own place and is left alone). It is a scroll, not a DOM mutation, and it uses the page's own scroll behaviour on purpose: a new smooth scroll takes over from the one under way, while an `instant` one was carried on by it and came to rest 2px to 60px off in most loads. A page whose sets hold one photo each loads no script and never gets shorter, so it needs none of this.
- The information (`shared/pages/project.html`, `client/project.css`) is plain server HTML: no component, no script. `.facts` holds the lines (`<p><span class="label">type:</span> …</p>`, the colon inside the Bold span, and `<p class="years">`), `.about` the `.description` and then `.links`; each is printed only if it has something in it, and `.neighbours` (a `<nav>`) only if there is an arrow. An arrow is `<a class="prev">` / `<a class="next">` with the project's address as `href` and `Previous project: <title>` / `Next project: <title>` as `aria-label`, around the same SVG path as the slideshow's chevrons, so the arrows work with JavaScript off and a project with one photo still loads no script. The left / right keys do not follow them: they move the set on screen as before, and nothing while the information is there. `loadContent()` in `server/content.js` gives every project `prevSlug`, `prevTitle`, `prevHref`, `nextSlug`, `nextTitle`, `nextHref` from its neighbours in `projects`, which is the Index list's order (published only, sub-items in their place); they are `''` at either end.
- The information's measures, all in `client/project.css`. From 760px `.project-info` is a grid of two `minmax(0, 1fr)` columns, so the line between them is the page's centreline, the one the header's title is centred on. `.facts` is 318px wide at the end of the first column (its 8px of right padding keep a long line as far from the centreline as the description is); `.about` starts 8px into the second and is at most 312px wide (in the owner's image the longest line is 306px and a word 8px longer wrapped). `align-items: baseline` puts the two first lines on one baseline whatever the engine's rounding: an 18.73px line carries its baseline 1px lower in its box than a 16px line does (1.37px before Chromium rounds it), so `.facts` has `margin-top: -1px` and starts at 73px while the description starts at 74px, both inside the section's 2px of top padding; that padding is why the section rests at 72px and not at 74px. The years' `margin-top: 18.73px` is the one empty line. The arrows are `position: absolute` in the section: `left: calc(50% - 359.25px)` is the centreline less 329px, less the 16.5px chevron, less the 13.75px the chevron sits into its 44px target; `calc(50% + 323.25px)` is 337px less that 13.75px; `top: calc(74.5svh - 94px)` is 74.5% of the window less the 72px the section rests at and half the target (`vh` where there is no `svh`). Columns and arrows need 2 × (337 + 16.5 + 13.75) = 734.5px, hence two columns from 760px, where the right target ends 12.75px from the page's edge. Below 760px everything is in the flow: `.facts`, 24px, `.about` (at most 433px), 24px, `.neighbours` as a flex row whose `.next` has `margin-left: auto`, so a lone arrow keeps its side; the targets stay inside the section's side padding, which is 16px, and 37px from 720px to 759.98px like the header's, so the text stays under `Back`.
- Two 8px measures keep a set at rest looking exactly as the one slideshow always did, where a photo that fills the height sits directly under the header with its frame's shadow reaching above it (the shadow is 2px down with a 6px blur; 8px is the furthest it reaches on any side, and Chromium paints 7 rows of it above the frame). The header's ground colour stops 8px above its bottom edge (a `background` 8px shorter than the box), so that shadow shows as before and everything above it is covered; and sets are 8px apart (`project-slides + project-slides`), so the next set's shadow is below the window's bottom edge while the set before it is at rest, instead of drawing a faint line there.
- The project page's `Back` link is plain `/`; the home page restores the filter that was active when the project was opened (sessionStorage, only on a followed link from `/projects/…`, never on reload).
- A caption is one line of Markdown in `images[].caption`; `*asterisks*` slant.
