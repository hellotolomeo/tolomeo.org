# tolomeo.org

Portfolio site for Tolomeo. Static, pre-rendered, hosted on GitHub Pages at tolomeo.org.
The spec is `BRIEF.md` (v2); decisions on the build plan are in `BUILD-PLAN-RESPONSE.md`. Read both before any change to layout, behaviour or content model. The **look** in `BRIEF.md` §3 and §5 and in `design/*.html` (dark, pink lines) is superseded: first by the redesign of 11 Nov 2026 (light), then by the redesign of 26 Nov 2026 (a Claude Design handoff, reviewed with the owner, and the owner's answers of that day), which builds on it and on the owner's requests of 18 to 20 Nov, and which the owner changed in three points the same day before it was published. The values that hold now are the "Design" section below.

## Stack
- The Zeldman Pattern, vendored in upstream's own `AGENTS.md` layout (`client/lib/`, `lib/vendor/`, `lib/filters.js`, `server/zeldman/`, docs in `lib/zeldman/`). One component = `components/<name>.html` + `.css` + `.js`. `setState()` is the only way a component's DOM changes. One script works outside the components: `client/zoom.js` makes one element, the opened picture, on a double click and appends it to `<body>`; it makes nothing on load. No inline `style=""` in any markup; generated proportions go in `dist/client/covers.css`, `dist/client/slides.css` and `dist/client/figures.css`.
- Node renders everything at build time: `node build.js` → `dist/`. No server in production.
- Pages (`server/routes.js` is the one list of them; there is no sitemap): `/` (and `/projects/`, the same page, pointing search engines at `/`), `/projects/<slug>/` for every published project, `/info/` (the About page, at the address it always had), `/collaborations/`, `/404.html`.
- Content is Markdown + YAML front matter in `content/`: `projects/<slug>.md`, `site/index.md` (the home page's intro and the site's description), `site/info.md` (About), `site/collaborations.md`. Images in `images/projects/<slug>/`, `images/info/` and `images/collaborations/`; the CMS stores full `/images/…` paths and drops empty keys, so the data layer defaults every field.
- Pages CMS edits content via `.pages.yml`. Keep the field names in `.pages.yml`, `content/` and the templates identical.
- GitHub Actions builds and deploys `dist/` on every push to `main`.

## Commands
- `npm run dev` — local server on http://localhost:3100 with live template reload
- `npm run build` — write `dist/` (resizes images with sharp, cached by hash)
- `npm run images -- <folder-of-originals> <slug>` — optional bulk tool: 2000px web copies in `images/projects/<slug>/`
- `npm run verify` — after a build: Playwright checks for the acceptance points and for the measures of the "Design" section (450 checks on 26 Nov 2026, about 3½ minutes; four of them run on a project page verify makes up for the run, which is never written to `dist/`: "The made-up project page" under Conventions). CI runs it on branches and PRs, not on `main`, so a save in the CMS is never held back by it, and a mistake typed in the CMS (a link to a page that does not exist) goes live unchecked. Needs Chromium: `npx playwright install chromium`, or `CHROMIUM_PATH`.
- `node scripts/normalize-images.js` — what CI runs before the build: HEIC/TIFF → JPEG, >2000px shrunk, content references rewritten (in a project's file and in a page of text's); idempotent.
- `scripts/import-site-data.js` (the import of the Claude Design site kit of 11 Nov 2026), `scripts/import-projects.py` (the first spreadsheet importer) and `scripts/import-covers.js` (the design-canvas cover migration) are **superseded: don't run them**. Content in `content/` (edited in the CMS) is the source of truth. The first would put the kit's photo lists, titles and texts back over the owner's list of 18 Nov 2026, drop every `images[].set`, unpublish projects the kit doesn't list, republish Pleasure Systems Archive and delete the photos added since; the second would bring back the spreadsheet's typos, old titles and publish states; the third writes `cover_style`/`cover_focus`/`cover_zoom`, which no longer exist.

## Rules
- Never edit `dist/`; it is generated.
- Never invent content: empty descriptions and missing images stay empty. Placeholders only where the design needs an image. The owner's rule of 26 Nov 2026: "do not write anything yourself in captions or otherwise." No text may appear on the site, visible or for assistive technology, that neither the owner's content nor the approved design gives. The words the templates print themselves (`back`, `previous`, `next`, `Projects`, `tags`, `type:` / `role:` / `for:`, `nothing here`, and the labels for assistive technology the site already had) are the design's or older; add no new one. So the descriptions of the About and the Collaborations picture (`alt`) are empty until the owner writes them in the CMS, both pages use the site's description, and a picture opened to the full window is named by the owner's words or not at all.
- Design values come from the "Design" section below (the redesign of 26 Nov 2026, which replaced `design/*.html`, the token table in `BRIEF.md` §3 and the values of 11 to 20 Nov where it says so). Don't restyle.
- Fonts: Fluxisch Else Light and Bold are the only font files. The handoff sets the home page's intro in Schwabacher Grotesk; the owner, 26 Nov 2026: "Use Fluxisch Else until I have the license for Schwabacher Grotesk." So the intro is Fluxisch Else Light in the handoff's colour and link style; its size is no longer the handoff's but the page's own, at the owner's request of the same day ("Design" below). Neither `SchwabacherGrotesk.ttf` nor the trial Katsu may be committed: no file, no `@font-face`, no mention in a `font-family`; `npm run verify` checks that the home page's stylesheets name no other family and that the build holds no other font file. When the licence is there: the file in `fonts/`, one `@font-face`, the family on `.site-head`, and that check changed with it.
- Plain JS, plain CSS, no bundler, no framework, no TypeScript. Dependencies stay: `nunjucks`, `gray-matter`, `marked`, `sharp`; `playwright` (pinned to the installed browser's version) is the only dev dependency, for `scripts/verify.js`.
- Every page must be complete HTML before JavaScript; the first browser render must make zero DOM mutations.
- Every `BRIEF.md` §9 assumption that still applies is a constant in `site.config.js` (the redesign of 11 Nov removed the hover photo and the frame jitter, and their constants with them).
- Anything Tolomeo edits must be editable alone in Pages CMS. Scripts are for one-off migrations only.

## Conventions
- Data flows one way: `server/content.js` shapes everything (sorting, defaults, image lookups, Markdown → HTML via `server/markdown.js`); templates only print flat fields. `build.js` and `server.js` share it and `server/routes.js`. Beside the projects it shapes the home page's text (`homeText()`), the two pages of text (`SHEETS`, `sheet()`) and the three generated stylesheets (`coversCss()`, `slidesCss()`, `figuresCss()`). A generated stylesheet is in three places: `loadContent()` returns its text, `build.js` writes it into `dist/client/`, and `server.js` answers its address with a line of its own (`/client/covers.css`, `/client/slides.css`, `/client/figures.css`); one added without that last line would be missing under `npm run dev` only.
- Components: `project-index` (home: grid + list + filter; props `projects, filter, match`, state `hover`) and `project-slides` (one set of a project page's photos, so a page has one per set; props `images, label, eager`, state `index, near`). Page-level styles: `client/site.css` (every page: the faces, the tokens, the body's type, `back`, the header of project pages and pages of text, the opened picture, the intro and the home page's column of window height, the 404 page's frame), `client/project.css` (project pages only: the two halves, the information, `previous` / `next`, the snapping) and `client/sheet.css` (pages of text only). Generated: `client/covers.css` (every page loads it: `--tag`, and for the home page `--dates` and a cell's proportions), `client/slides.css` (project pages with photos), `client/figures.css` (a page of text with a picture). Scripts: `client/main.js` (home) and `client/project.js` (a project page with a set of several photos) are the page entries; `client/zoom.js` is loaded by every page with a content picture (a project page with a photo, a page of text with a picture). A project whose sets hold one photo each loads `zoom.js` and nothing else, and its `<project-slides>` is never defined; a page of text loads no project stylesheet.
- Browser-only template variables (`shown`, `hover`, `index`, `near`) are guarded with `| default(…)` so the server render and the first browser render are identical. Keep it that way; `npm run verify` measures it.
- Templates are preloaded with `fetch()` by `client/template-env.js` `setup([...])`; list every template (and partial) a page's components use in that page's entry (`client/main.js`, `client/project.js`).
- No comments in CSS (`lib/zeldman/AGENTS.md`); the derivations live here.
- The intro (`homeText()` in `server/content.js`, `shared/pages/index.html`, `.site-head` in `client/site.css`). `intro` is one field of several lines (a YAML block scalar, `intro: |-`): it is split at line ends, every line trimmed, the empty ones dropped, and each put through `markdownInline`, so each line is one line of Markdown (`[words](address)`, `**bold**`, `*slanted*`). `site.intro` is the list of those HTML strings; the template prints them inside the header's one `<p>`, each as `<span class="l">`, one space between two and none before the first or after the last; with no line the `<p>` is left out and the header is its padding (46px from 720px, 82px below). Below 720px `.l` is `display: block` and 12px under the one before (both rules inside `max-width: 719.98px`); from 720px it is an ordinary inline. The base rule is `text-wrap: balance` for the phone's centred blocks and the 720px block sets it back to `wrap`: without that the running paragraph is balanced and every line ends well short of the margin. `.site-head` sets no `font-size`, so the intro has the body's, which changes at 720px (14.5px, then 12.5px), and no `line-height` below 720px, where it has the body's 18px; the one size or line it sets is `line-height: 18px` in its 720px block, where the body's line is 15.2px. `scripts/verify.js` holds the two apart: `HOME_BODY` and `HOME_TYPE` for the page, `HOME_INTRO` and `HOME_STEP` for the intro. `.site-head a` only sets the underline's 1px; the colour, the 3px offset and the hover are the sitewide `a` rule's. `site.description` (the meta description of the home page and, through `server/routes.js`, of About and Collaborations) is a field of its own, `description`, plain text with white space collapsed; left empty it is the intro's words (`markdownText`), and with both empty no page prints the tag. (Until 26 Nov it was always the intro's words, which would now be four sentences.) The designer's version still sets the text as the handoff did, in Schwabacher Grotesk at 15px / 21px: 1383.8px on one line there (in Fluxisch Else at that size it was 1594.3px here), two lines in a header of 88px at 800px and at 1366px, where this build has two lines in 82px. So the header differs between this build and the designer's version by the font, the size and the line.
- From 720px the index fills what the intro leaves (`client/site.css`, `components/project-index.css`): `body:has(project-index)` is a flex column of `100dvh` (with `100vh` before it), `main` is `flex: 1 1 auto; min-height: 0`, and `project-index` is `height: 100%` of it (a flex item of a column of definite height has a definite height after flexing, so the percentage resolves). The fallback is real, not a cascade trick: `project-index` has `height: calc(100vh - 82px)` and the `dvh` twin, and `height: 100%` is inside `@supports selector(:has(a))`. (The handoff wrote both in one rule, where `100%` always wins, and where `:has()` is missing `100%` of an auto-height `main` is `auto`: the index was as tall as its content and the page scrolled over the whole grid.) Where `:has()` is missing the index is the window less 82px, the header with two lines (34 + 2 × 18 + 12; it was 88px while the intro's line was 21px, and whoever changes the intro's line or padding changes this length with it): exact for an intro of two lines, 18px too tall for one of three (the page scrolls by 18px), 18px too short for one of one (measured with `:has()` made to fail in the stylesheets on their way to the browser, at 740, 1024, 1366 and 1700px wide). `body` has no `overflow: hidden` (the handoff had it): nothing overflows, and without it a window lower than the intro can still be scrolled to read it. The document is exactly the window at every size tried from 720 × 400 to 1920 × 1080.
- `cqw` on the home page. `project-index` is the query container of the grid and the list, and from 720px it is `box-sizing: border-box; padding: 0 20px; column-gap: 29px`, so there **`100cqw` is the page less 40px, no longer the page**; below 720px it has no padding and `100cqw` is the page. Its two sections are `flex: 1 1 50%` with `min-width: 0`: (100cqw − 29px) / 2 each. The grid's two columns are `calc(25cqw - 7.25px)` each, half a section, written as that length and not as `minmax(0, 1fr)`: where scroll-driven animations are not supported the native scrollbar of `.scroll` shows, and with `1fr` it would make the cells narrower than their `sizes` says, while with a fixed length it lies over the right cells' margin (`.grid` is `overflow-x: clip`). The date cell's limit is derived from the same container (the point "The list's date column" below). Every `.cell` is a container too: inside it `cqw` is the cell's own width. The list's date column is not a share of anything: it is as wide as the widest date a row prints, the same at every width. Type does not scale with the page. Each column starts with a strip: `flex: none; box-sizing: border-box; height: 29px; border-bottom: 0.67px solid var(--line)`. Over the grid it is generated (`.images::before`), since it holds nothing; over the list it is real markup, `<div class="head">`, the first child of `<section class="index">`: `<span class="years"></span><span class="what"><span class="title">Projects</span><span class="tags">tags</span></span>`. It reuses a row's classes on purpose, so the very rules that lay out a row lay it out and the words cannot drift from the columns: `.row` and `.head` share the two-track grid, the 27.2px gap and the padding `0 16px 0 12px`; its empty `.years` prints the unseen `--dates` text like every row's date cell, so it has the date column's width whatever the dates are and whichever rows a filter leaves; its `.what` is the same 11 : 10 grid; `.title` gives `Projects` the titles' Bold, `.tags` gives `tags` the types' colour and slant. Two consequences: a selector that means the rows' own must say `.row .years` (`project-index .years` alone also matches the strip's cell), and `project-index .head { display: none }` must stay after the shared `.row, .head` rule, which sets `display: grid` (same specificity). From 720px `.head` is `display: grid; align-items: start; line-height: 24px; white-space: nowrap`; below 720px it is not displayed and not read out. The words are within 0.004px of their columns at 720, 800, 1024, 1366 and 1920px, with and without a filter; verify holds them to 0.1px. `.head` is `overflow: hidden` with `scrollbar-gutter: stable`, like `.rows`, because it lies outside the list's scroller: where a classic scrollbar shows (no scroll-driven animations), the rows are narrower than the strip by its width and the types' column would start 11/21 of that left of the word `tags`; with the gutter on both, both lose the same. For that the two gutters must be one width, and two things that look removable on a box that never shows a scrollbar see to it. `.head` has `scrollbar-width: thin` like `.rows`, because a gutter is as wide as the scrollbar it is kept for (in Chromium here 10px for a thin one, 15px otherwise): without it, where a classic scrollbar shows, the strip's gutter is 15px for the rows' 10px and `tags` stands 2.6px left of its column. And `.head` is in the two `:is(.scroll, .rows, .head)` selectors of the `@supports (animation-timeline: scroll())` block, the first of which sets `scrollbar-width: none`: out of that one, where the thumbs are drawn by the stylesheet (today's Chromium), the strip keeps a 10px gutter the rows do not have and `tags` stands 5.25px left of its column. (Both measured in Chromium at 1024 × 600 with the stylesheet changed on its way to the browser; taking `.head` out of the second selector alone, `::-webkit-scrollbar`, changed nothing there.) One case is left: a browser with neither scroll-driven animations nor `scrollbar-gutter` (Safari before 18.2) that shows classic scrollbars puts `tags` about half a scrollbar right of its column.

(Measuring: a slanted type list reports its lean in `getBoundingClientRect()`, 1.6px more than the width the layout and the slide work with.) Each column is `<span class="clip">` and its text `<span class="line">` inside it (the title link and nothing else; for the types `.line.tags`, the buttons); a project without tags has no second `.clip` and the grid keeps its place. Below 720px `.clip` is `display: contents` and `.line` an ordinary inline, so the phone list is the flow it always was. Rows are centred (`align-items: center`), not on a baseline: not every browser gives a `container-type` box a baseline, and every cell is one 15.2px line anyway. - Cut, fade and slide, without a script. `.clip` is `overflow: clip` (it cuts and is not a scroller, so where the device can hover it can never be left scrolled; the `overflow: hidden` before it is for browsers without `clip`, where the text is then cut and faded but does not slide), `container-type: inline-size` (inside it `100cqw` is the column's width) and has a `mask` gradient that is opaque up to `100% - 1em` and transparent at the right edge: that is the fade, over the last 1em (12.5px; written in `em`, it followed the type), with no overlay and no ground colour in it. `.line` is a block of `max-content` width with `padding-right: calc(1em + var(--ring))`. In `translate` a percentage is the line's own width, so `min(0px, 100cqw + var(--ring) - 100%)` is the column less the text less 1em: 0 when the text ends before the fade (it then never moves), otherwise exactly the shift that puts the end of the text where the fade begins. The steady speed: `--index-slid`, a registered `<length>`, goes from 0 to 1000px in 10s, linear, while the row is `.on` or `:hover` (100px a second; 1000px is far more than any text overhangs), and the line's `translate` is `max(-1 * var(--index-slid), <the stop>)`, so every text travels at the same speed and stops at its own end. The way back: that value is multiplied by `--index-keep`, a registered `<number>` that is 1 while the row is pointed at and 0 otherwise, and takes 0.2s, linear, either way. When the pointer leaves it goes to 0 while `--index-slid` is held where it was by a 0.2s `transition-delay` and only then drops to 0, unseen: the text goes home in a straight 0.2s from wherever it was. On the way in it is why the start is not on the line at once: for the first 0.2s the text is at 500t² px instead of 100t (at most 5px behind, at 0.1s, never faster than 200px a second) and level with the line from then on. That start is the price of a pointer that comes back before the text is home (it wobbles between two rows): `--index-keep` turns round where it is and `--index-slid` goes on from where it was held, so the text glides back to where the slide stands, at the speed it was going home with; with `--index-keep` set to 1 at once (`0s`, as it first was) the start was exactly linear, and that pointer saw the text jump tens of pixels in one frame. The types stand still under the pointer: `.row:is(.on, :hover) .tags:hover` gives `--index-slid` another target (2000px, which it never travels to) behind a `transition-delay` of a day, the same hold as on the way back, so the list stays where it is, at rest or slid, for as long as the pointer is on it; without that a tag slid away from under the pointer before the click, and the first tags of a cut list could not be clicked at all. The target must not be 0px: that is the rest value, and leaving the row from a tag would then start no new transition, the hold would go on and the next slide would start where the last one stood. Only a type list is ever held: the rule is on `.tags`, the types' own `.line`, and a title's line goes on at 100px a second while the pointer is on the types. When the pointer goes from the types to the title or the date the type list goes on from the held length to 1000px in the same 10s, so a little under 100px a second (measured: 96 from a held 31.7px, 90 from 91.7px; by arithmetic 89.6 at the least for a list that still has a way to go, since the type list that overhangs the most does so by 104.3px, at 720px). The rule is before `.clip:has(.tag:focus-visible) .line` in the file, which has the same specificity and must win. (Tried first and dropped: a transition on `translate` for the way back, which Chromium starts from the style without the travelled length, so the text snapped back; and `--index-slid` itself running back to 0 in 0.2s, which spends most of that time beyond the stop, where nothing shows.) Where `@property` is not supported the two are plain values that cannot transition: the text jumps to its end and back, and the types do so under the pointer as well (the hold is a transition too). Under `prefers-reduced-motion: reduce` the transitions are off and the same happens: the end is simply shown (the hold on the types keeps its delay there, so pointing at the types still moves nothing).
- `--ring` is 5px: the room a focus ring needs, 2px of line 2px from the element, and 1px for the lean of the slanted types (7.6px × tan 6° = 0.80px, in a 15.2px line). `.clip` has it as left padding under an equal negative margin (so the column's text still starts on the column's edge), and its mask hides that strip, all but its last pixel, while nothing in it has keyboard focus, so a sliding text is cut 1px left of the column's left edge and not 5px left of it. The mask's opaque part starts at `var(--ring) - 1px` and not on the edge itself because a column starts on a fraction of a pixel: a hard stop there is snapped to a whole pixel and erased the pixels in which a first letter (J, T, W) begins, also where nothing is cut. `.clip:has(:focus-visible)` gets the same above and below and shows the strip, so the ring is whole. A tag with keyboard focus must be seen: `.clip:has(.tag:focus-visible)` becomes a scroller (`overflow: hidden`, `scroll-snap-type: x mandatory`) and the focused tag is its one snap target (`scroll-snap-align: start`), so the browser brings that tag to the column's left edge, as far as the text goes (`scroll-padding` is the ring on the left and 1em plus the ring on the right, and the line's right padding gives the last tag the way to come clear of the fade with its ring). The snap is needed because Chromium does not scroll to a focused element of which a part already shows. In that column the slide is off while a tag has focus (`--index-slid: 0px; --index-keep: 0; transition: none`), so pointing at the row adds no second shift; when focus leaves, the column is `overflow: clip` again, which has no scroll position, so it shows its start. It is `:focus-visible`, not `:focus-within`, on purpose: a tag clicked with the mouse must not move under the pointer, or the click misses it. One case is left, and accepted: while a tag has keyboard focus and its column is scrolled to it, a mouse press on another tag of the same column takes the focus, the column is `overflow: clip` again and back at its start, so another tag is under the pointer when the button comes up and that one click filters by nothing (a scroll position cannot outlive the scroller, and nothing in CSS can hand it to `translate`). A title is one link: with keyboard focus its row is `.on`, so a cut title slides to its end like under the pointer. On screens that cannot hover (`hover: none`, still 720px or wider) nothing slides: a column is `overflow-x: auto` without a scrollbar and is dragged sideways with a finger; a tap on a tag filters as ever. There the line's right padding is 1em without the ring's 5px, so a column can be dragged exactly when its text reaches the fade, and as far as its end at the fade's start, the same stop as the slide (with the 5px a text that fits could be dragged by up to 5px; the cost is that the ring of a last tag focused from a keyboard on such a screen reaches up to 4px into the fade; the slanted types lean 0.8px over either end, which a scroller counts, so their way is a pixel or two longer). A column there is the visitor's to drag and keeps the position a finger, or a tag focused from a keyboard, gave it: a scroller's position cannot be reset from CSS.
- Grid thumbnail: `width: min(88cqw, 49.9733cqw * var(--a))`, where `49.9733cqw` is 86.5% of the cell's height as a share of its width (197.12 / 341.2 × 86.5) and `cqw` the cell's own width.
