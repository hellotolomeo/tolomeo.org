# tolomeo.org

Portfolio site for Tolomeo. Static, pre-rendered, hosted on GitHub Pages at tolomeo.org.
The spec is `BRIEF.md` (v2); decisions on the build plan are in `BUILD-PLAN-RESPONSE.md`. Read both before any change to layout, behaviour or content model. The **look** in `BRIEF.md` §3 and §5 and in `design/*.html` (dark, pink lines) is superseded by the redesign of 11 Nov 2026: its values are the "Design" section below.

## Stack
- The Zeldman Pattern, vendored in upstream's own `AGENTS.md` layout (`client/lib/`, `lib/vendor/`, `lib/filters.js`, `server/zeldman/`, docs in `lib/zeldman/`). One component = `components/<name>.html` + `.css` + `.js`. `setState()` is the only way the DOM changes. No inline `style=""` in component markup; generated proportions go in `dist/client/covers.css` and `dist/client/slides.css`.
- Node renders everything at build time: `node build.js` → `dist/`. No server in production.
- Content is Markdown + YAML front matter in `content/` (projects, site). Images in `images/projects/<slug>/`; the CMS stores full `/images/…` paths and drops empty keys, so the data layer defaults every field.
- Pages CMS edits content via `.pages.yml`. Keep the field names in `.pages.yml`, `content/` and the templates identical.
- GitHub Actions builds and deploys `dist/` on every push to `main`.

## Commands
- `npm run dev` — local server on http://localhost:3100 with live template reload
- `npm run build` — write `dist/` (resizes images with sharp, cached by hash)
- `npm run images -- <folder-of-originals> <slug>` — optional bulk tool: 2000px web copies in `images/projects/<slug>/`
- `npm run verify` — after a build: Playwright checks for the acceptance points (CI runs it on branches and PRs, not on `main`). Needs Chromium: `npx playwright install chromium`, or `CHROMIUM_PATH`.
- `node scripts/normalize-images.js` — what CI runs before the build: HEIC/TIFF → JPEG, >2000px shrunk, content references rewritten; idempotent.
- `scripts/import-site-data.js` (the import of the Claude Design site kit of 11 Nov 2026), `scripts/import-projects.py` (the first spreadsheet importer) and `scripts/import-covers.js` (the design-canvas cover migration) are **superseded: don't run them**. Content in `content/` (edited in the CMS) is the source of truth. The first would put the kit's photo lists, titles and texts back over the owner's list of 18 Nov 2026, drop every `images[].set`, unpublish projects the kit doesn't list, republish Pleasure Systems Archive and delete the photos added since; the second would bring back the spreadsheet's typos, old titles and publish states; the third writes `cover_style`/`cover_focus`/`cover_zoom`, which no longer exist.

## Rules
- Never edit `dist/`; it is generated.
- Never invent content: empty descriptions and missing images stay empty. Placeholders only where the design needs an image.
- Design values come from the "Design" section below (the redesign of 11 Nov 2026, which replaced `design/*.html` and the token table in `BRIEF.md` §3). Don't restyle.
- Plain JS, plain CSS, no bundler, no framework, no TypeScript. Dependencies stay: `nunjucks`, `gray-matter`, `marked`, `sharp`; `playwright` (pinned to the installed browser's version) is the only dev dependency, for `scripts/verify.js`.
- Every page must be complete HTML before JavaScript; the first browser render must make zero DOM mutations.
- Every `BRIEF.md` §9 assumption that still applies is a constant in `site.config.js` (the redesign removed the hover photo and the frame jitter, and their constants with them).
- Anything Tolomeo edits must be editable alone in Pages CMS. Scripts are for one-off migrations only.

## Conventions
- Data flows one way: `server/content.js` shapes everything (sorting, defaults, image lookups, Markdown → HTML via `server/markdown.js`); templates only print flat fields. `build.js` and `server.js` share it and `server/routes.js`.
- Components: `project-index` (home: grid + list + filter; props `projects, filter, match`, state `hover`) and `project-slides` (one set of a project page's photos, so a page has one per set; props `images, label, eager`, state `index, near`). Page-level styles are `client/site.css` (every page, with the Index header and the Info / 404 frame) and `client/project.css` (the project page's header and information).
- Browser-only template variables (`shown`, `hover`, `index`, `near`) are guarded with `| default(…)` so the server render and the first browser render are identical. Keep it that way; `npm run verify` measures it.
- Templates are preloaded with `fetch()` by `client/template-env.js` `setup([...])`; list every template (and partial) a page's components use in that page's entry (`client/main.js`, `client/project.js`).
- Measures the design gives as a share of the 1366px page are `cqw` on a page-wide container (`project-index`; `main.project`), so they scale with the page and ignore the scrollbar; at ≥720px the grid's two columns are `25cqw` each for the same reason (where the native scrollbar shows, it lies over the right cells' margin instead of shrinking them). The list's date column is not such a share: it is as wide as the widest date, the same at every width (the last point of this list). Type stays 13px. Nothing wraps from 720px up: a row is `white-space: nowrap` with a fixed `height: var(--row)`, and text that has no room is cut and slides (the next point), so at every width a row is one 23px slot. The date cannot wrap either: the column fits every date, up to 40% of the list, and one longer than that (a sentence: the CMS takes any text) is cut at its cell's edge, where the chevron's 27.2px begin, without a fade, instead of printing over the title (`.years` is `overflow: clip visible`, sideways only, so no glyph loses its top or bottom).
- The list's columns (`components/project-index.css`, everything in `min-width: 720px`). The row keeps its two tracks (the date's, `max-content`, then `.what`, 27.2px after it: the last point of this list); `.what` is a grid of `minmax(0, 11fr) minmax(0, 10fr)` with a 15px gap, which is the 11 : 10 split of what is left: at 1366px the list is 683px, less 22.9px of left padding, 68.4px of dates (the widest date, 36.2px, and the 32.2px) and 16px of right padding leaves 575.7px, less the gap 560.7px, so 293.7px and 267.0px. With the content of 19 Nov 2026 the widest title is 234.6px and the widest type list 185.0px, and a text has its column less 1em (281.7px and 255.0px): nothing is cut at 1366px or wider; of the 58 texts 3 are cut at 1024px, 12 at 800px, 22 at 720px. Each column is `<span class="clip">` and its text `<span class="line">` inside it (the bullet and the title link; for the types `.line.tags`, the buttons); a project without tags has no second `.clip` and the grid keeps its place. Below 720px `.clip` is `display: contents` and `.line` an ordinary inline, so the phone list is the flow it always was. Rows are centred (`align-items: center`), not on a baseline: not every browser gives a `container-type` box a baseline, and every cell is one 16px line anyway (the text sits where it sat at 1366px, measured). The chevron is `.what::before`, outside both columns, so nothing cuts it and nothing pushes it.
- Cut, fade and slide, without a script. `.clip` is `overflow: clip` (it cuts and is not a scroller, so where the device can hover it can never be left scrolled; the `overflow: hidden` before it is for browsers without `clip`, where the text is then cut and faded but does not slide), `container-type: inline-size` (inside it `100cqw` is the column's width) and has a `mask` gradient that is opaque up to `100% - 1em` and transparent at the right edge: that is the fade, over the last 13px (1em), with no overlay and no ground colour in it. `.line` is a block of `max-content` width with `padding-right: calc(1em + var(--ring))`. In `translate` a percentage is the line's own width, so `min(0px, 100cqw + var(--ring) - 100%)` is the column less the text less 1em: 0 when the text ends before the fade (it then never moves), otherwise exactly the shift that puts the end of the text where the fade begins. The steady speed: `--index-slid`, a registered `<length>`, goes from 0 to 1000px in 10s, linear, while the row is `.on` or `:hover` (100px a second; 1000px is far more than any text overhangs, the most today is 116px at 720px), and the line's `translate` is `max(-1 * var(--index-slid), <the stop>)`, so every text travels at the same speed and stops at its own end. The way back: that value is multiplied by `--index-keep`, a registered `<number>` that is 1 while the row is pointed at and 0 otherwise, and takes 0.2s, linear, either way. When the pointer leaves it goes to 0 while `--index-slid` is held where it was by a 0.2s `transition-delay` and only then drops to 0, unseen: the text goes home in a straight 0.2s from wherever it was. On the way in it is why the start is not on the line at once: for the first 0.2s the text is at 500t² px instead of 100t (at most 5px behind, at 0.1s, never faster than 200px a second) and level with the line from then on. That start is the price of a pointer that comes back before the text is home (it wobbles between two rows): `--index-keep` turns round where it is and `--index-slid` goes on from where it was held, so the text glides back to where the slide stands, at the speed it was going home with; with `--index-keep` set to 1 at once (`0s`, as it first was) the start was exactly linear, and that pointer saw the text jump tens of pixels in one frame. The types stand still under the pointer: `.row:is(.on, :hover) .tags:hover` gives `--index-slid` another target (2000px, which it never travels to) behind a `transition-delay` of a day, the same hold as on the way back, so the list stays where it is, at rest or slid, for as long as the pointer is on it; without that a tag slid away from under the pointer before the click, and the first tags of a cut list could not be clicked at all. The target must not be 0px: that is the rest value, and leaving the row from a tag would then start no new transition, the hold would go on and the next slide would start where the last one stood. When the pointer goes from the types to the title or the date the slide goes on from the held length to 1000px in the same 10s, so a little under 100px a second (92 at worst, from the type list that overhangs the most, 79px at 720px). The rule is before `.clip:has(.tag:focus-visible) .line` in the file, which has the same specificity and must win. (Tried first and dropped: a transition on `translate` for the way back, which Chromium starts from the style without the travelled length, so the text snapped back; and `--index-slid` itself running back to 0 in 0.2s, which spends most of that time beyond the stop, where nothing shows.) Where `@property` is not supported the two are plain values that cannot transition: the text jumps to its end and back, and the types do so under the pointer as well (the hold is a transition too). Under `prefers-reduced-motion: reduce` the transitions are off and the same happens: the end is simply shown (the hold on the types keeps its delay there, so pointing at the types still moves nothing).
- `--ring` is 5px: the room a focus ring needs, 2px of line 2px from the element, and 1px for the lean of the slanted types (8px × tan 6° = 0.84px). `.clip` has it as left padding under an equal negative margin (so the column's text still starts on the column's edge), and its mask hides that strip, all but its last pixel, while nothing in it has keyboard focus, so a sliding text is cut 1px left of the column's left edge and not 5px left of it. The mask's opaque part starts at `var(--ring) - 1px` and not on the edge itself because a column starts on a fraction of a pixel: a hard stop there is snapped to a whole pixel and erased the pixels in which a bullet or a first letter (J, T, W) begins, at 1366px as well, where nothing is cut. `.clip:has(:focus-visible)` gets the same above and below and shows the strip, so the ring is whole. A tag with keyboard focus must be seen: `.clip:has(.tag:focus-visible)` becomes a scroller (`overflow: hidden`, `scroll-snap-type: x mandatory`) and the focused tag is its one snap target (`scroll-snap-align: start`), so the browser brings that tag to the column's left edge, as far as the text goes (`scroll-padding` is the ring on the left and 1em plus the ring on the right, and the line's right padding gives the last tag the way to come clear of the fade with its ring). The snap is needed because Chromium does not scroll to a focused element of which 32px already show. In that column the slide is off while a tag has focus (`--index-slid: 0px; --index-keep: 0; transition: none`), so pointing at the row adds no second shift; when focus leaves, the column is `overflow: clip` again, which has no scroll position, so it shows its start. It is `:focus-visible`, not `:focus-within`, on purpose: a tag clicked with the mouse must not move under the pointer, or the click misses it. One case is left, and accepted: while a tag has keyboard focus and its column is scrolled to it, a mouse press on another tag of the same column takes the focus, the column is `overflow: clip` again and back at its start, so another tag is under the pointer when the button comes up and that one click filters by nothing (a scroll position cannot outlive the scroller, and nothing in CSS can hand it to `translate`). A title is one link: with keyboard focus its row is `.on`, so a cut title slides to its end like under the pointer. On screens that cannot hover (`hover: none`, still 720px or wider) nothing slides: a column is `overflow-x: auto` without a scrollbar and is dragged sideways with a finger; a tap on a tag filters as ever. There the line's right padding is 1em without the ring's 5px, so a column can be dragged exactly when its text reaches the fade, and as far as its end at the fade's start, the same stop as the slide (with the 5px a text that fits could be dragged by up to 5px; the cost is that the ring of a last tag focused from a keyboard on such a screen reaches up to 4px into the fade; the slanted types lean 0.84px over their end, which a scroller counts, so their way is a pixel or two longer). A column there is the visitor's to drag and keeps the position a finger, or a tag focused from a keyboard, gave it: a scroller's position cannot be reset from CSS.
- No comments in CSS (`lib/zeldman/AGENTS.md`); the derivations live here. Grid thumbnail: `width: min(91cqw, 49.9733cqw * var(--a))`, where `49.9733cqw` is 86.5% of the cell's height as a share of its width (197.12 / 341.2 × 86.5). Until 19 Nov 2026 both limits lost 12px for the 6px border and the border was drawn outside that; now the picture itself is what fits them, so the side that limits it lies exactly where the frame's outer edge was, and the other side, which follows from the picture's proportions a : 1, differs from the old frame's by 12px × (a − 1) across a picture limited by its height (4.5px more on either side for the widest thumbnail, 1.9px less for the narrowest) and by 12px × (1/a − 1) down a picture limited by its width. That `cqw` is the cell's own width (every `.cell` is a container), so below 720px, where a cell is the page wide and has no fixed proportion (`aspect-ratio: auto`), the same line limits a thumbnail to 91% of the page's width and 49.9733% of it in height. `coverSizes()` in `server/content.js` says the same in `sizes` (a cell is a quarter of the page from 720px, the whole page below), so a phone takes a file sharp enough for its larger thumbnail. Slideshow (`components/project-slides.css`): `--head` 79px is the page header; `--cap` 63px is the caption's room (16px gap, three 13.2px lines, 7.4px), kept on every slide so a photo that fills the height sits directly under the header; `--h` is what is left of the viewport (`svh`); `--w` is the page less, on each side, a 44px chevron target, a 14.25px gap (the 16.5px chevron is centred in its target, so that puts it 28px from the photo) and a 16px edge; at ≤600px the gap and edge are 0. The photo is `width: min(var(--w), var(--h) * var(--a))`, neither limit losing the 12px it lost for the border until 19 Nov 2026: at 1366 × 710 a photo of 1.4995 is 851.7 × 568, where its frame was 845.7 × 568 around a picture of 833.7 × 556, and one of 3.3333 is 1217.5 × 365.3 (its frame was 1217.5 × 373.6). A photo limited by width instead of height is centred in the slide. The caption's limit is 512px because its 16px side padding is inside it: 480px of text.
- A picture is never cropped: its box (`.box` in the grid, `.frame` on a project page; both names are from when the box had a border, and they stay because the HTML, the two component stylesheets, `project-slides.js` (a click on `.frame`) and the checks use them) has only its `box-shadow`, no border, no padding and no background, so a picture that has not loaded yet is an empty box with its shadow. The picture is stretched over the whole box (`object-fit: fill`), not fitted into it: the box has the original's proportions to four decimals, but the resized file the browser takes is a whole number of pixels each way and so a fraction off them (a 1000 × 581 original's 600px file is 600 × 349: 1.7192 for 1.7212), and with `contain` Chromium then drew the picture a whole pixel short on one side, which left a line of the ground colour between the picture and its shadow (4 of the 29 thumbnails at 1366px; unseen while that pixel lay against the paper border). The stretch is that rounding and no more, half a pixel of the file's height (0.15% at most, with today's files); `scripts/verify.js` checks the `fill`. Only a picture whose size the build could not read (`width=""`, so no `--a` and a 3 : 2 box; none today, it would take a GIF or SVG that sharp cannot measure) stays `contain`, so it is never distorted. - The list's date column (`components/project-index.css`; `coversCss()` in `server/content.js`; 19 Nov 2026). The build writes one more rule into `client/covers.css`, `project-index{--dates:"…"}`: a CSS string of every distinct date as printed (the published projects' `years` after `shortYears()`, in list order, white space as one space, as a row prints it), a date to a line. Every row prints that string in its date cell, unseen: `.years::after` has `content: var(--dates)` and is a block with `white-space: pre`, `height: 0`, `overflow: hidden` and `visibility: hidden`. It inherits the cell's font, size and weight, so each of its lines is exactly as wide as that date is in its row and follows the type when that changes; a date cell's `max-content` width is therefore the widest date's, the row's first track is `max-content`, and every row has the same column whichever rows a filter leaves. The 32.2px are the cell's `padding-right: 5px`, the air, and the row's `column-gap: 27.2px`, what the chevron takes (`.what::before` at `left: -27.2px`), so the chevron's box starts 5px after the end of the widest date. The air is inside the cell because the cell clips sideways: with the cell's edge on the very end of the widest date, the clip took the faint last pixel off that date's last figure at some widths (1440px, 1920px). Why each part is as it is: `::after` and not `::before`, because below 720px a row is `align-items: baseline` and a block that clips and has no height gives its own top edge as its baseline; first in the cell that was the cell's first baseline, and every date sat 12px under its title's line, while after the date the cell's first baseline is the date's own line. `overflow: hidden`, because without it the unseen lines add to what the list (below 720px, the page) scrolls over under the last row. `visibility: hidden`, because generated content is read out otherwise; it is in no node of the page, so the server's HTML is what it was and the first render still makes no mutation. In the string, letters, digits, spaces and `, . -` stand as they are and every other character is a hex escape with the space that ends it (`\2019 ` the apostrophe, `\2013 ` the dash, `\a ` the line between two dates, `\22 ` a double quote, `\5c ` a backslash), so nothing typed in the CMS can end the string or the rule and the file is ASCII; with no date at all there is no rule, `content` is then invalid and the cell has no such box. The limit: `.years` has `max-width: calc(20cqw - 32.2px)` from 720px up (the list is `50cqw`, so that is 40% of it less the air and the gap) and `calc(40cqw - 32.2px)` below, so the date column, air and gap included, never takes more than 40% of the list. It is a `cqw` length because a percentage there would be a share of the very track it sizes, and count as no limit. A date longer than that is cut at its cell's edge from 720px up, where a row is one line (it ends where the chevron's box begins, not under it); below 720px it wraps inside its cell, and only a single word longer than the cell is cut (`.years` is `overflow: clip visible` at every width). A date's own text counts for its own row as well, being in the cell, which changes nothing in a build, where `--dates` has every date the rows print. With the dates of 19 Nov 2026 the string holds 13 dates and begins `"\2019 26\a \2019 23\2013 26\a \2019 25, 26\a …`; the widest is `’25, 26`, 36.2px in Bold 12px, so the column is 68.4px and at 1366px the title's column starts 91.2px from the list's edge (6.68% of the page).
